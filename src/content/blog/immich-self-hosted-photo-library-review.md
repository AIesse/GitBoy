用 iCloud 或 Google Photos 存照片，时间久了会遇到三个绕不开的问题：容量一直涨、订阅一直续；照片里的地点、人脸、时间被平台拿去做索引；以及最要命的一点——**这些照片其实不在你手里**，账号出问题或者服务调整策略，你只能被动接受。

想把照片拿回自己硬盘的方案一直有，但大多不好用：要么只是个文件夹同步工具，没缩略图、没时间轴、手机上翻几十万张照片能卡死；要么是十年前那套相册软件，界面停留在 PC 时代，手机端基本没有。

**Immich 是这套需求目前完成度最高的开源答案：一个自托管的照片与视频管理服务，手机 App 自动备份，网页端提供时间轴、地图、相册、人脸聚类和语义搜索，所有文件和数据都落在你自己的机器上。**

它在 GitHub 上约有 11.9 万 star，用 AGPL-3.0 协议开源，最新稳定版 v3.4.2 发布于 2026 年 11 月 18 日，最近一次代码提交就在今天——这是一个每周都在发版的活跃项目。

## 一、核心功能

### 手机端自动备份，重复文件自动跳过

Immich 的使用方式跟 Google Photos 很像：手机装 App，填上你自己服务器的地址，登录之后照片就开始往你的硬盘里传。备份是「App 打开时自动触发」的方式，也可以手动点一下立即开始；支持只备份指定相册，而不是把整个相册库都塞上去。

它会对文件做去重判断，同一张照片重复上传不会在库里出现两份。这一点在换手机、重装系统时很关键——你不会得到一份图片内容相同、文件名不同的混乱库。

### 时间轴的性能是真的做了优化

照片一多，最考验相册软件的就是滚动流畅度。Immich 的时间轴用了虚拟滚动，也就是只渲染屏幕范围内可见的缩略图，滚动条可以按年份、月份快速拖动定位。几万张照片的库在这种实现下不会像传统瀑布流那样越滚越卡。

同时它还处理了几类容易被普通相册忽略的格式：RAW 原片可以直接识别，Live Photo / Motion Photo 能备份也能播放，360 度全景图在网页端可以拖动查看。

### 搜索靠的是语义 + OCR + 人脸

Immich 的搜索不是简单地按文件名匹配。它把 Postgres 直接当作搜索数据库，装上 VectorChord 扩展后，用 CLIP 模型给每张图算向量，于是可以这样搜：

- **语义搜索**：输入「海边的日落」「生日蛋糕」，即使照片没有任何关键词标注也能命中；
- **图片内文字（OCR）**：截图里的菜单、路牌、票据上的字可以直接搜到；
- **人脸**：自动识别并聚类出「人物」，按人筛选；
- **地点与反向地理编码**：按城市、省份、国家筛；
- **文件名、扩展名、文件夹路径、描述、标签**：这些偏「工程」的检索维度也都保留着。

这几项组合起来，基本覆盖了「我记得有这么一张照片，但想不起在哪」的全部找法。

### 多用户、共享相册与合作伙伴共享

Immich 从设计上就是个多用户系统，不是单人玩具。管理员在后台建账号，每个用户的照片互相隔离；同时可以建共享相册给家人看，也可以用「合作伙伴共享」把某个人的整个图库按权限共享给你——比如夫妻两人各自备份，但都能看到孩子的照片。

对家庭自托管来说，这个设计比「所有人共用一个账号」要合理得多。

### 元数据、地图与「那年今日」

每张照片的 EXIF 都能查看，包括相机型号、光圈快门、拍摄坐标，位置会落到一张全局地图上，可以按地图缩略图浏览某地拍过的所有照片。它还有 Memories 功能，把「去年今天」「三年前的这一周」这类回忆聚合成一个入口。

这些功能单独看都不新鲜，但开源方案里能一次性做齐的不多。

## 二、适合哪些使用场景？

- **想把照片从云服务迁回本地的人**：几百 GB 的图库，长期订阅成本并不低，迁到自己的 NAS 或小主机上，硬件是一次性投入。
- **家里有多台设备、多个人要备份**：手机、平板、相机卡统一进一个库，按账号隔离，再按需共享。
- **对隐私敏感的场景**：照片、人脸、位置数据全在局域网内，不出内网也能用。
- **本来就有 NAS 或常开小主机的人**：硬件已经在跑，加一个容器几乎零边际成本。
- **需要一个能对外分享单张照片/相册的轻量方案**：生成公开链接分享，不用把原图发到聊天软件里被压缩。

反过来说，如果你的照片总共不到几千张、也完全不在意云服务，那折腾一套服务端的收益可能不如直接用手机自带相册。

## 三、优点与注意事项

**优点**

- 功能完整度高，备份、浏览、搜索、共享、多用户形成闭环，不是半成品。
- 手机端体验接近商业产品，iOS 和 Android 都有官方 App，不是套壳网页。
- 社区极活跃，版本迭代快，文档写得比多数开源项目细。
- 数据完全自持：照片是普通文件按目录存放，数据库是标准 Postgres，随时可以整体搬走。
- 有官方演示站（demo.immich.app），装之前可以先摸一遍界面。

**注意事项**

- **硬件门槛不低**。官方要求至少 6GB 内存、推荐 8GB，CPU 至少 2 核、推荐 4 核。4GB 内存的机器只能关掉机器学习功能勉强跑。一台常年开机的老笔记本或低配 ARM 盒子，跑起来会比较吃力。
- **磁盘要留余量**。缩略图和转码后的视频会让图库体积平均增加 10%–20%，Postgres 数据库本身通常还要占 1–3GB。
- **它只支持 Linux 系的部署方式**。官方推荐 64 位 Linux，非 Linux 系统靠 Docker Desktop 或 WSL2，官方明确说明这类环境下排障支持会弱很多。
- **没有原生桌面客户端**。官方特性表里只区分「移动端」和「Web」，电脑上就是浏览器打开，不要期待一个 Mac/Windows 应用。
- **v3 之后对 CPU 指令集有要求**。amd64 平台上的机器学习容器需要 `x86-64-v2` 微架构，2012 年之后的 CPU 基本都支持；如果你的机器更老，最后一个能用的版本是 v2.7.5，而那个版本已经不再维护。
- **备份策略不能只靠它**。官方在 README 里专门挂了警告，提醒按 3-2-1 原则做备份——自托管不等于自动安全，硬盘坏了照样全没。

## 四、安装方式

官方推荐 Docker Compose，也是唯一推荐的正式部署方式。整套服务由四个容器组成：

![Immich 四容器部署结构与端口关系](/GitBoy/images/immich-self-hosted-photo-library-review/04-architecture.jpg)

- `immich-server`：唯一对外暴露的服务，默认映射 2283 端口，同时提供 Web 界面和 REST API；
- `immich-machine-learning`：跑 CLIP 与人脸识别推理，按需挂 CUDA / OpenVINO / RKNN 等加速；
- `redis`：实际用的是 Valkey 镜像，负责任务队列与缓存；
- `database`：官方定制版 PostgreSQL 14，已内置 VectorChord 向量扩展。

部署流程大致是这样：准备一个目录，下载官方发布的 `docker-compose.yml` 和 `.env` 示例文件，改掉 `.env` 里的上传路径、数据库密码和版本号，然后 `docker compose up -d`。首次启动后访问 `http://服务器IP:2283`，创建管理员账号，再在手机 App 里填这个地址登录即可。

有一个细节值得注意：官方文档明确要求使用**当前发布版本**对应的 `docker-compose.yml`，仓库主分支上的那个文件可能跟最新 release 不兼容。直接从 release 页面下载对应版本的 compose 文件最稳。

常用命令：

```bash
# 拉取当前版本对应的编排文件
wget -O docker-compose.yml \
  https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml

# 启动
docker compose up -d

# 升级：改 .env 里的 IMMICH_VERSION 后
docker compose pull && docker compose up -d
```

## 五、综合评价

Immich 属于那种「把商业产品的体验按开源方式重做一遍」的项目，而且完成度确实到了能日常用的程度。它最难得的地方不是功能多，而是**功能之间是连起来的**：备份进来的照片能立刻被索引、能被人脸聚类、能被语义搜索、能被共享出去，这条链路是通的。

代价是要有一台像样的机器，并且接受自己承担运维责任——硬件、备份、升级、出问题自己修。它不适合完全不想碰命令行的人。

如果你本来就有一台常开的 NAS 或小主机，且对照片存在别人服务器上这件事一直不太舒服，那 Immich 是目前最值得试的一个。官方有演示站，不用装就能先看界面，觉得合适再动手。

**一句话评价：把 Google Photos 的体验搬到自己硬盘上，代价是一台 8GB 内存的机器和一点运维耐心。**
